Feluda workflow guide

A customer asks for a website change. A Care lead turns it into an approved plan, a builder makes the edit in WordPress, and Feluda checks the live site before anything is called done. This page shows each person's steps and what every button does.

Care lead

Login care.lead in the dev seed. Owns the request from start to finish.

  • Logs requests and checks the plan Feluda drafts
  • Approves what will be built
  • Decides cases Feluda can't judge
  • Runs the final check and closes the request

Builder

Logins builder.one, builder.two. Owns individual jobs.

  • Picks up jobs that are Ready
  • Edits the WordPress site by following the steps
  • Clicks Mark done so Feluda verifies the change
  • Fixes and resubmits if verification fails

Feluda (automatic)

Runs in the background; nobody clicks for these.

  • Transcribes voice notes, crawls the site, plans jobs
  • Takes "before" screenshots of each target
  • Captures the live site and judges each change
  • Drafts the done message for the customer

Three screens matter: the Queue (home page, list of requests), the Request page (one customer request, its requirements and jobs), and the Job card (one change on the site). A request is split into one or more jobs.

Care lead workflow

Seven stages. The Queue's New request button and the Metrics tab only appear for Care leads.

  1. Log the customer's request

    Queue (home page) · bottom of the page

    Paste the request exactly as the customer sent it. Email and ticket systems can also create requests automatically, so some will already be in the queue.

    New request
    Scrolls down to the New customer request form. It does not create anything by itself.
    Plan this request
    Creates the request from the form: website URL (required), customer, channel (ticket, email or voice), request text, and optional screenshots or voice notes. Opens the new Request page.
    Feluda then transcribes any voice notes, crawls the site and drafts requirements and jobs. The status moves through transcribing and parsing to needs review, or to plan failed.

  2. Unblock planning, if it stalls

    Request page · Customer request and Planner panels
    Save transcript
    Type what the customer says in a voice note. Planning starts once every voice note has text.
    Only shown when the request is awaiting transcript because automatic transcription failed.
    Re-plan
    Inside "Re-plan with a clarification". Adds your clarification to the request text and runs the planner again from scratch.
    Use it when the status is plan failed, when the customer's wording was vague, or after you get an answer to a requirement marked "needs clarification".

  3. Review requirement coverage

    Request page · Requirement coverage table and Jobs table

    Feluda lists each thing the customer asked for (R1, R2…) with the words it came from. Every requirement must be covered by a job or deliberately excluded before you can approve.

    Save (per row)
    Records your decision for one requirement: covered by jobs, needs clarification, or excluded (reviewed), plus a note. Exclusions need a reason and appear in the evidence report.
    Any change makes an earlier approval out of date, so you will need to approve again.
    Job title link
    Opens that job's card so you can check the exact element, the current → desired value, the pages and viewports, and the builder steps.
    A job showing "blocker(s)" or "Recipe: none" will not become ready until you correct it.

  4. Correct jobs and attach images

    Job card · "Correct this job" and "Approved replacement image"
    Save correction
    Inside "Correct this job". Edits the job: title, recipe, current and desired value, links, region, element type, page URLs, desktop/mobile, "old value must be absent", menu order and known exclusions. A reason is required and logged.
    Creates a new revision (r2, r3…) and sends the job back to needs review, so the coverage map must be approved again. On a closed request it reopens the request and voids the done message.
    Use this image
    Uploads the customer's approved replacement image (PNG, JPEG or WebP) for an image-swap or logo job.
    Image jobs cannot become ready without an approved image. Needs re-approval afterwards.
    Draft image
    Asks Muse Image to generate a candidate from your prompt. Use it only when the customer asked for new visuals.
    The draft appears below with its own buttons.
    Approve Reject
    On a Muse Image draft. Approve makes it the approved replacement image (re-approval needed). Reject discards it.

  5. Approve the plan

    Request page · bottom of Requirement coverage
    Approve coverage map
    Confirms you checked the original request, its attachments and the planned jobs. Feluda then captures "before" screenshots of every target; each job without blockers becomes ready for builders.
    Greyed out while any requirement is unresolved; the red line above it names which. If the before-capture can't find the target uniquely, that job goes to needs human.

  6. Handle exceptions while builders work

    Job card · primary action panel (top)

    The Queue's Stuck column links straight to jobs that need you.

    Record decision
    Resolves a needs human job. Pick one decision and write a note (required, shown to the builder):
    • Change is wrong, return to builder → job goes back to the builder
    • Mark failed with my note → job shows as failed; the builder fixes and resubmits
    • Scope/target problem, send back to review → job returns to needs review for you to correct
    There is deliberately no "mark passed" option. The first two are only allowed after the builder has started.
    Recapture baseline
    Takes the "before" screenshots again, for example after the target couldn't be found or the capture timed out.
    Only before the builder starts; after that the original baseline is kept.
    Retry verification
    Reruns a verification that broke for technical reasons (site unreachable, browser error). Builders can click it too.
    Only on verification error. This is not a judgement on the change.

  7. Close and report to the customer

    Request page · Close request · and the Evidence report

    Until every job has passed, this section lists what is still missing instead of the button.

    Freeze checkbox
    Run final consistency gate
    Tick the box to confirm every builder has finished editing, then click. Feluda freezes edits on that site, recaptures every affected page on desktop and mobile, reruns all checks, and closes the request as done. It then drafts the done message.
    Shown when the request is ready to close. If something changed on the site meanwhile, the affected job goes back and the request stays open. Builders see a freeze banner and can't start or submit until it ends.
    Evidence report
    Top of the Request page. One page per request: requirements, each job's verdict, every check, and before/after screenshots.
    Print / PDF JSON export
    On the evidence report. Save it as a PDF to send with the done message, or download the same data as JSON.
    Feluda never emails the customer. You review and send the done message yourself.

Also available to Care leads

Metrics (top navigation): request volume, pass rates and model cost across the customers you can access. The Model calls and Background tasks panels at the foot of a Request page show what Feluda ran and anything that errored.

Builder workflow

Six stages. Builders see the same Queue and Request pages but without the planning and approval controls.

  1. Find a job to work on

    Queue → Request page → Jobs table

    Open a request whose status is with builder, then open a job marked ready. Jobs in needs review are still with the Care lead; you can't start them yet.

    Tip: the Queue's Stuck column links straight to jobs that failed or need attention.

  2. Read the job card before touching the site

    Job card
    Exact element
    What to change: current value → desired value, the link, the pages, and desktop/mobile. The "Before" screenshot shows the exact spot.
    Steps
    Click-by-click WordPress instructions from a validated recipe for this site. "Recipe snapshot" shows the raw template and values.
    Acceptance criteria
    Exactly what Feluda will check after you click Mark done. Items tagged required must all pass.
    Exclusions, Depends on
    Places you should not change, and jobs that must pass before this one can start.
    Download approved image
    On image and logo jobs. The image to upload to WordPress. Verification compares images visually, so WordPress renaming or resizing it is fine; a different or stretched image fails.

  3. Start the job

    Job card · primary action panel
    Start this job
    Assigns the job to you and moves it to with builder. Locks the original "before" screenshots so later comparisons use them.
    Greyed out if you're logged in as a Care lead or a site freeze is running. Refused with a message if a prerequisite job hasn't passed, the Care lead's approval is out of date, or another job is already editing the same shared header or footer.
    Side effect on shared areas: starting a job on a header, footer or menu sends other passed jobs on that same area back for re-verification, since your edit could affect them.

  4. Make the change in WordPress

    Outside Feluda · the customer's WordPress admin

    Follow the Steps. Check the public site, not just the editor, on every listed page and on mobile if listed. Clear any cache so the public page shows the change.

  5. Submit for verification

    Job card · primary action panel
    Mark done
    Tells Feluda the public site is ready. It captures each listed page at each viewport, checks the target text, link, image or menu order, confirms the old value is gone where required, submits contact forms to the test inbox, and flags changes outside the target. The page refreshes itself while verifying.
    Available while the job is with builder or failed. Clicking twice is safe; it reuses the same submission. Greyed out during a site freeze.

  6. Act on the result

    Job card · Latest verification
    ResultWhat it meansWhat you do
    passedEvery required check passed.Nothing. The Care lead closes the request once all jobs pass.
    failedAt least one check failed. Each check lists why, with before/after screenshots.Fix the site and click Mark done again. From the second failure, Feluda adds a diagnosis note.
    needs humanFeluda couldn't decide (e.g. the visual judge was unsure).Wait. The Care lead will return it to you with a note, fail it, or send it back to review.
    verification errorA technical problem stopped the check. It says nothing about your change.Click Retry verification.
    Save correction
    Builders can also edit the job (for example if the "current value" doesn't match what's really on the site). A reason is required.
    This sends the job back to needs review; the Care lead must re-approve before you can continue. Tell them why.
    When the yellow Site edit freeze banner appears, the final check is running. Don't edit that site until it disappears.

Why is this button greyed out?

ButtonUsual reasons
Approve coverage mapA requirement is still "needs clarification" or has no job. The red line above the button names it.
Start this jobYou're logged in as a Care lead; a site freeze is running; a prerequisite job hasn't passed; the approval went out of date after a correction; another job is editing the same shared area.
Mark doneYou're logged in as a Care lead; a site freeze is running; the job isn't started yet.
Run final consistency gateNot every job has passed, or approval is out of date. The list above the button says which. The freeze checkbox must be ticked.
Retry verificationOnly appears on a verification error, and not during a site freeze.
